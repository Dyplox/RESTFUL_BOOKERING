# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An API **test-automation** suite (not an API) against the public Restful Booker API (`https://restful-booker.herokuapp.com/`), built with Serenity BDD + Screenplay + Cucumber + RestAssured. Tests hit the live API, so they need network access and results depend on its state (the public API resets its data periodically). Project language is Spanish: feature files, step text, class names (`CrearToken`, `GuardaToken`), README and `docs/CONTEXTO.md` (full architecture + known-issues reference — keep it in sync when behavior changes).

## Commands

`gradlew` is not executable in git; use `sh ./gradlew` (or `chmod +x gradlew`). Build is Gradle; `pom.xml` is a leftover template and is not used.

```bash
sh ./gradlew compileTestJava                                   # compile only
sh ./gradlew clean test                                        # all tests + Serenity report
sh ./gradlew test --tests 'co.booker.runners.BookingRunner'    # one feature (AuthRunner, BookingRunner, PingRunner)
sh ./gradlew sonarqube                                         # static analysis
```

- To run a single scenario, tag it in the `.feature` and add `tags = "@tag"` to the runner's `@CucumberOptions` (Gradle does not forward `-Dcucumber.options` to the test JVM). No scenarios are tagged today.
- `ignoreFailures = true`: the build prints `BUILD SUCCESSFUL` even when tests fail. Check the console `FAILED` lines, `build/test-results/test/*.xml`, or the report at `target/site/serenity/index.html` (generated by `aggregate`, which always runs after `test`).

## Java 27 / Serenity compatibility

Toolchain is Java 27 with Gradle 9.9.1, but Serenity is 3.3.9-RC3 (ByteBuddy 1.12). The `test` task in `build.gradle` therefore sets `--add-opens java.base/java.lang=ALL-UNNAMED` and `net.bytebuddy.experimental=true`. Removing either brings back `Cannot define class using reflection` failures. The real fix is upgrading Serenity. Gradle 9 has no `jcenter()`; use `mavenCentral()`.

## Architecture (Screenplay)

Flow: `.feature` (Gherkin `# language: es`) → step definitions (`src/test/java/co/booker/stepdefinitions`) → `theActorInTheSpotlight().attemptsTo(Task)` → Task in `src/main/java/co/booker/tasks` issues a Serenity REST interaction (`Get.resource`, `Post.to`, `Put.to`, `Patch.to`, `Delete.from`) → assertions via `should(seeThat(Question, matcher))`.

Key cross-file conventions:

- **Stage/actor setup lives in `AuthDefinition`**: its `@Before` creates the `OnlineCast` and reads `restapi.baseurl` from `serenity.properties`; the step `Dado que Abel quiere logueaser en la Api` gives actor `Abel` the `CallAnApi` ability. Every feature starts with that step, and all runners share the glue package `co/booker/stepdefinitions`, so `AuthDefinition` steps are used by all features.
- **Shared assertion steps** (also in `AuthDefinition`/`PingDefinition`): `el verifica que el codigo HTTP sea {int}`, `el deberia recibir el token y validar el esquema {string}` (despite the name, used for any response body), `el deberia ver un tiempo menor a {int}`. Reuse these instead of adding new ones.
- **Questions read the last response globally** (`SerenityRest.lastResponse()`), not a per-actor value: `CodigoRespuestaHttp` (status), `TiempoRespuestaHttp` (ms). Assertions always apply to whichever request ran last.
- **Auth token passing**: `CrearToken` POSTs `/auth`; `GuardaToken` reads `token` from the last response and stores it with `actor.remember(Constantes.TOKEN, ...)`; update/delete tasks `actor.recall(TOKEN)` and send it as `Cookie: token=...`. `DeleteBookingBasicAuth` uses a hardcoded Basic header instead.
- **Tasks are created with `Tasks.instrumented(Class, args...)`**, so the args must match a public constructor exactly (Serenity instantiates via reflection). Endpoints come from the `uris` enum (`AUTH`, `BOOKING` = `"booking/"`, `PING`); request bodies are hand-built JSON strings (the `Booking`/`BookingDates` models exist but are unused; `User`/`Location`/builders are template leftovers).
- One runner per feature in `co.booker.runners`, using `CucumberWithSerenity`. A new feature needs a new runner.

## Known pitfalls (details in `docs/CONTEXTO.md` §8)

- The `src/test/resources/*.json` files used by "validar el esquema" are **sample responses, not JSON Schemas**: object-shaped ones accept anything, and `getBookingIds.json` (an array) throws `invalid JSON Schema`. Write real schemas (`type`/`properties`/`required`) when touching them.
- `GuardaToken.ingreso()` calls `instrumented(GuardaToken.class)` but the class only has a `String` constructor, which causes an NPE in every scenario using "el Guarda el token".
- Booking scenarios use fixed IDs (11, 1212, 1214), which fail intermittently against the shared live API.
- Invalid-login scenarios expect 200 + `token.json`; the API actually returns 200 with `{"reason":"Bad credentials"}`.
- Baseline as of the Java 27 migration: 10 tests, 2 pass. None of the failures are caused by the JDK.
